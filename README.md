# Сервис заказа такси

##### 1. Таблица ответственности классов (Принцип единственной ответственности)

| Класс или интерфейс        | Ответственность (строго одно предложение без запрещенных союзов)                                      |
|----------------------------|-------------------------------------------------------------------------------------------------------|
| PricingStrategy            | Определяет единый контракт расчета стоимости поездки для всех алгоритмов ценообразования.             |
| PricingContext             | Делегирует вычисление итоговой стоимости поездки текущему назначенному алгоритму ценообразования.     |
| StandardPricingStrategy    | Рассчитывает базовую стоимость поездки по фиксированным тарифам за километры с минутами.              |
| SurgePricingStrategy       | Вычисляет повышенную стоимость поездки путем умножения базового тарифа на внешний коэффициент спроса. |
| AirportFlatRateStrategy    | Возвращает фиксированную неизменную стоимость для специализированных поездок в аэропорт.              |
| DriverMatchingStrategy     | Задает общий интерфейс выбора оптимального водителя из списка доступных кандидатов.                   |
| DriverMatchingContext      | Перенаправляет задачу поиска подходящего водителя активному выбранному алгоритму подбора.             |
| NearestDriverStrategy      | Выбирает водителя с минимальным физическим расстоянием до точки посадки клиента.                      |
| HighestRatedDriverStrategy | Находит водителя с максимальным показателем пользовательского рейтинга среди доступных кандидатов.    |
| LongestIdleDriverStrategy  | Назначает на заказ водителя с наибольшим временем ожидания без поездок.                               |
| Driver                     | Хранит неизменяемые данные водителя об идентификаторе, дистанции, рейтинге, времени простоя.          |
| StrategySelector           | Выбирает подходящие стратегии автоматически на основе анализа текущих параметров поездки.             |
| DemandSensor               | Предоставляет интерфейс получения внешних данных о коэффициенте спроса в конкретной зоне.             |
| Assignment5Demo            | Демонстрирует работу всех алгоритмов, автоматический выбор селектором, смену стратегии на лету.       |

##### 2. Стратегия против Состояния против Шаблонного метода

В предметной области заказа такси требуются взаимозаменяемые алгоритмы для расчета 
стоимости поездки (`StandardPricingStrategy`, `SurgePricingStrategy`, `AirportFlatRateStrategy`) 
и подбора водителей (`NearestDriverStrategy`, `HighestRatedDriverStrategy`, `LongestIdleDriverStrategy`). 
Использование шаблона «Стратегия» позволяет менять эти алгоритмы во время выполнения программы через метод смены 
стратегии в классах контекста (`PricingContext`, `DriverMatchingContext`), а также добавлять новые тарифы без 
модификации существующего кода в соответствии с принципом открытости/закрытости.

Шаблон «Стратегия» выбран вместо шаблона «Состояние», поскольку оба класса контекста не меняют свое поведение 
автоматически в результате внутренних переходов жизненного цикла объекта. В шаблоне «Состояние» 
сами объекты состояний часто знают друг о друге и инициируют переход контекста из одного этапа в другой
(например, заказ переходит от статуса «Поиск» к статусу «В пути»). В нашей задаче расчет цены — это 
разовая независимая операция: поездка не переходит самостоятельно из режима «Стандарт» в режим «Аэропорт». 
Конкретный алгоритм выбирается извне клиентом или классом `StrategySelector` на основе внешних факторов 
(час пик, срочность заказа, статус клиента) и передается в контекст для выполнения вычисления.

Шаблон «Стратегия» предпочтительнее «Шаблонного метода», так как реализованные алгоритмы полностью 
отличаются по своей внутренней механике, а не просто переопределяют отдельные шаги одного общего 
алгоритмического скелета. Например, фиксированный тариф аэропорта (`AirportFlatRateStrategy`) 
сразу возвращает константу без учета дистанции, стандартный тариф складывает стоимость километров со 
временем, а пиковый тариф (`SurgePricingStrategy`) обращается к внешнему датчику `DemandSensor`. 
Кроме того, «Шаблонный метод» базируется на наследовании, жестко привязывая подклассы к базовому классу 
на этапе компиляции и лишая систему возможности менять алгоритм у уже созданного объекта на лету. 
Наше решение использует композицию и делегирование через интерфейсы, полностью изолируя бизнес-логику расчетов от классов контекста
